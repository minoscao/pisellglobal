# Global Growth · 从线索到正式客户的数据架构

11 Sep 2026 · 业务数据设计 v2 · 尚未建库、连接系统或启动 Agent

最新规则见 [V0–V3 入围判断](V0-V3-QUALIFICATION.md)：V0 收录全部已发现且符合范围的对象，包括筹备、规划、在建和已营业；V1 按规划/在建/营业问题或升级筛选；V2 客户表示兴趣后进入正式跟进；V3 已签业务协议或实际支付意向金。AI 自主扩展搜索特征，门槛仍由事实与审核支撑。

本文件落实用户最新确认的 V1 / V2 / V3 商业主线。这里的 V 是业务转折点，不是软件版本。它更新早期图中 Customer Profile 的叫法：前期建立企业与项目档案，V3 才取得正式客户身份。部门工作分类仍沿用完整工作图；本次是商业主线的数据专题。

## 核心结构

**企业档案是身份，项目档案是现实中的事情，商机档案是我们争取的这笔生意。V1、V2、V3 是这笔生意的三个有依据的转折点。**

企业第一次进入系统时就有固定档案，后续只补全资料和关系，不在每次升级时复制。一个集团可以有多家经营公司、多个业态和场馆；同一项目也可以有分期采购或不同合同范围的商机。每笔商机独立推进，避免把集团中一家店的签约误当成整个集团全部签约。

共享信息关系：一个企业可以关联多个项目；一个项目可以涉及业主、运营商、设备商等多个企业，各自标注角色；一个商机有主要采购方和明确项目范围，可覆盖多个场馆。企业未查明时也能先保留候选项目，不能凭空补运营商。

“Venue Project”指客户新开店、扩店、改造、集团系统建设等事情；部门的参展、制作画册等“Work Project”仍是工作容器，两者可关联但不可混用。集团系统项目不强制填写场馆图纸或地址。

## 三个转折点怎样成立

| 转折点 | 成立依据 | 形成的结果 | 不足以成立的情况 |
| --- | --- | --- | --- |
| V0 · All Relevant Records | 符合范围的已发现游乐场对象或具体筹备意向，不论现实阶段 | 建立或匹配企业、场馆/项目/意向、证据，未知字段待补；未入 V1 也保留 | 全量收录不代表全网覆盖，不把重名、泛泛话题或效果图素材当具体场馆 |
| V1 · Worth Following | 负责人核对项目证据、产品匹配理由和可执行的下一步，确认值得投入跟进 | 建立商机，关联原企业、项目和全部线索；记录负责人、确认日期、理由、下一动作 | 搜到帖子、地图有商户、AI 打分高，都只算候选 |
| V2 · Customer Confirms Interest | 对方明确表达愿意继续讨论需求、演示或方案，保留回复或经记录的会议结论、联系人与确认内容 | 进入正式 Follow-up，推进经营需求、正式方案和报价 | 邮件送达、已读、AI 推测、内部做完效果图，不代表客户意向 |
| V3 · Signed / Intent Payment Received | 已签署的业务协议，或实际收到且可归属这笔交易的意向金；保留签署文件或收款核实记录 | 建立交易及正式客户关系；具备范围时关联订单，范围未定则待确认，不自动交付 | 报价已发、客户口头说会付、发票已开、仅签保密协议，都不代表成交 |

每次过关保留：哪笔商机、哪个转折点、发生时间、确认人、依据、当时方案/报价版本。系统计算当前进度，页面不能另外维护一套状态。V3 签约与意向金采用“或”，不要求必须同时完成；签约也不等于已收款。付款性质与约定独立记录，意向金不被自动改称定金或尾款。

直接询价、展会线索、转介也接入这条主线，不强迫先做全网扫描。若一次来信同时满足多个门槛，可在同次审核中分别记录真实依据，无需制造虚构跟进记录。

## 需要保存的十二组业务记录

这些是资料的归属，不是要求界面出现十二个菜单。

| 资料组 | 保存什么 | 怎样连接和复用 |
| --- | --- | --- |
| 1. 企业与联系人 | 企业、品牌、集团归属、业务单元、官网、社交主页、客户类型；联系人职务、所属公司、公开业务联系方式和来源 | 企业只有一份；潜在买方、正式客户、伙伴可以是同一企业的不同关系。三类客户类型沿用 Venue Management / Single Business / Diversified Business |
| 2. 项目与场馆 | 建什么、在哪里、涉及场馆、运营商/业主角色、现场条件、规划与开业时间线 | 未知项留空；地址与坐标保留依据和精度。商场坐标不等于已找到铺位，拟开业时间不等于确认开业时间 |
| 3. 线索与证据 | 原始链接、来源、内容片段、发布日期、事件日期、发现时间、涉及项目、事实/推断、可信程度 | 多篇信息汇入同一项目；转载同一公告不算多个独立证据。后续纠正保留原记录和替代关系 |
| 4. Alert 与核查 | 触发事件、变化前后、触发理由、缺失信息、核查结论、负责人、处理状态 | Alert 指向项目和证据，不是另一份商机。新事件提醒，重复转载不重复建项目；有意义的变化才重新提醒 |
| 5. 商机 | 采购方、项目范围、匹配理由、来源归属、负责人、下一步、预计采购窗口、当前商业进度 | V1 后成立；同企业多商机分别跟进。来源同时保留首次发现、关键转介和实际推动成交的记录 |
| 6. 经营与需求 | 运营模式、业务模块、目标、语言和当地条件、当前系统、约束、缺项、确认人和日期 | 按企业/项目保留事实，商机引用本次需求版本。国家资料是参考，不能自动变成客户已确认要求 |
| 7. 沟通与行动 | 电话/会议/邮件记录、客户反馈、承诺、负责人、到期日、下一动作和执行结果 | 同一时间线关联企业、项目、商机。AI 建议与实际已发送、已开会的记录分开 |
| 8. 提案与展示 | 所用素材、客户品牌、图纸、初步策略、演示、布局、效果图、3D 展厅、假设、版本、审核和反馈 | 每个产物关联本次需求及输入版本；初步概念与客户认可版本区分。资料包是上述记录的汇总视图/导出快照，不重新抄一份事实 |
| 9. 正式方案与报价 | 经营方案、软件模块、硬件数量、配置、定制、排除项、金额/币种、有效期、审批与客户接受版本 | 引用既有报价系统的正式记录和编号；方案变更生成新版本，不覆盖旧报价。不从效果图猜数量或价格 |
| 10. 转折点确认 | V1/V2/V3、确认人、时间、事实依据、对应回复/会议/协议/收款和内容版本 | 同一商机的历史记录，可追溯修正；AI 可以建议，不能自行假装客户表达了意向 |
| 11. 订单、协议与收款 | 成交主体、商机、成交范围、批准报价、合同版本、签署、定金/尾款、实际收款和退款记录 | 一个企业可有多笔订单；付款独立于合同。分期款可以对应同一订单。正式客户身份由有效成交记录产生，不再建第二份公司资料 |
| 12. 交接与接收 | 客户购买目标、承诺、批准范围、软件包、硬件包、各自接收人、版本和待补项 | 同一订单分给 TIM / Software Configuration 和 Procurement / Hardware Purchase；硬件包括规格、数量、批准颜色及图案。两方独立确认接收 |

共享素材库独立于商业阶段，沿用 Readiness / Sales Materials 的唯一归属：产品能力、标准模块、案例、画册、演示场景等。商机引用素材及版本，不为每个客户复制整套基础库。原始文件只保存一份，通过关联用于不同产物；客户专属修改作为派生版本保留。

## AI 怎样随项目情况准备不同内容

| 当前取得的资料 | AI 准备的可审核结果 | 记录中的必要区分 |
| --- | --- | --- |
| 只有筹建消息 | 商机摘要、缺项、跟进理由、基于标准场景的品牌化 3D Demo、首次联系草稿 | 场景为演示；不是客户真实场地。记录 Logo 来源和可用情况，缺少品牌资料先用占位 |
| 已有效果图或规划材料 | 产品整合示意、业务模块建议、适用时的 3D 展示、需要客户补充的问题 | 标注输入来源；没有尺寸依据的图不当施工布局，不承诺可安装数量 |
| 已取得图纸和明确需求 | 结合经营方式与本地条件的布局、配置、定制边界、正式方案及报价准备 | 区分客户确认、内部确认和仍待核实项；技术/价格承诺经对应人员确认 |
| 项目延期或出现新变化 | 更新档案摘要、重排跟进时间、说明旧提案受影响的部分 | 保留历史，标记需要重做的版本，不重新生成一套无关客户档案 |

AI 运行还需留下：本次目的、读取的证据/素材/需求版本、生成时间、结果、缺项及失败原因，便于复核。完整资料包可以在第一次人工跟进前准备好；它不意味着已得到客户确认。对外发送及新承诺遵守已授权范围，本次未执行外联。

## 四种状态各管一件事

| 维度 | 唯一含义与建议状态 |
| --- | --- |
| 现实项目进度 | 沿用资讯库 announced / planning / construction / opening / open / postponed / cancelled / unknown；项目实体变化，不是销售进度 |
| 商业转折点 | V0 / V1 / V2 / V3，由有效确认记录得出；V0 是收录层，V1 前没有正式商机身份 |
| 跟进处置 | active / on_hold / closed_lost / disqualified；watchlist 属于候选线索管理，成交由 V3 记录得出 |
| 证据可信度 | 沿用 confirmed / probable / unverified / disputed；事实是否站得住，不代表客户有购买意向 |

Alert 审阅状态继续使用资讯库的 new / reviewed / snoozed / resolved，不能与上述状态互相代替。预计开业月份、最近核实时间、下一跟进时间分别保存。

延期可让跟进暂停但不抹掉已确认意向；客户拒绝记录原因；发现误判撤销对应确认并保留轨迹。合同取消、退款另记在订单与付款记录，保留历史客户事实并显示当前关系，不删除企业。现有客户的新项目仍从自身证据推进，不能继承其他订单的 V3。

## 前台怎么呈现

保留现有品牌与共享布局，采用 Global Alerts / Opportunities / Customers 三个入口及共享 Library。

- Global Alerts：世界事件地图＋最新变化清单，点开同一项目证据包；圈选现有场馆作为辅助工具。地图只显示有依据的位置，缺地址的线索仍可留在列表。
- Opportunities：V1 与 V2 的商机，可切 List / Map / Board；地图按关联场馆显示，同商机多场馆不重复计数。
- Customers：至少一笔有效 V3 成交的企业，展开全部项目、商机和订单；保留其其他尚在 V1/V2 的商机。
- 同一个详情框架：Overview / Evidence / Activity / Solution / Commercial。内容按资料与权限呈现，切换视图保留选择和筛选。
- 顶部同时显示项目情况与商业转折点。默认给最新摘要、负责人、下一步，长证据和版本历史在详情展开。

部门原有 Dashboard / Projects / Map 仍为同一部门工作集合的视图，不被此商业专题取代。统计分别使用线索事件、现实项目、商机、成交企业、订单的数量；不把同一项目的十条帖子计作十笔商机。

## 与现有资料及工具的衔接

现有 intelligence/venue-opportunities.json 中的来源、项目、Alerts 和运行记录继续作为发现端的事实资料；现有 Alert 不自动升级 V1。本次只提出结构，未迁移这些记录、未创建真实商机或客户。

后续实施先核实既有 CM、报价、素材库的记录与入口，再确定正式归属和连接。既有 quotation 是报价来源，资料包只是引用。现阶段不选数据库品牌、不新建第二套报价、不声称自动实时覆盖全球。

历史数据图尚未反映最新 V0 和意向金规则；当前以 [入围判断](V0-V3-QUALIFICATION.md) 为准。新版信号图见 [Global Playground Signals](global-playground-signals-v3.png)，画面中的场景为概念示意。
